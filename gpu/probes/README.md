# Hardware probes for the attention design

Small hand-written CUDA programs that settle the hardware questions `ATTENTION.md` §4.4 lists, before the attention
kernel is built on the answers. Each is standalone (it includes only `probe.h` from this directory), runs one CTA of
128 threads on an sm_100a GPU, and prints what it found and a verdict. None is generated by Raccoon.

| Probe | Experiment | Assumption | What it settles |
|---|---|---|---|
| `h1_tmem_a.cu` | H1 | A23 | The layout of a bf16 A operand in tensor memory (P in the second product): which lane is which row, which 16-bit half holds the lower k, how many columns a K = 16 step reads |
| `h2_mn_major_b.cu` | H2 | A24 | The MN-major B descriptor (V without a transpose): the transpose-B bit, LBO between the two 64-wide halves of N, SBO between 8-row groups of K, the 2048-byte K step |
| `h3_tmem_align.cu` | H3 | A27 | Which tensor-memory column offsets `tcgen05.mma` (D and A) and `tcgen05.ld`/`st` accept, and whether data lands exactly there |
| `h5_accum_error.cu` | H5 | §1.3 | The tensor cores' f32 accumulation error for 128 × 128 × 128 bf16, against the sequential-sum bound T1 assumes |

H4 (the ordering of A20 and A21) is a stress test of the A1 kernel itself and has no probe here.

## Running

```bash
gpu/probes/run.sh            # all probes
gpu/probes/run.sh h1 h2      # some, by prefix
```

`run.sh` builds each probe with `nvcc -std=c++17 -O2 -gencode arch=compute_100a,code=sm_100a` (CUDA 12.9; no
`-lcuda`: the probes use only the runtime API), runs it under `timeout` (`PROBE_TIMEOUT`, default 900 seconds per
probe), keeps binaries and logs in `$OUT` (default a fresh `/tmp/probes.*`), and ends with a table: per probe, the cases
that passed, its exit status and its verdict. Exit status 0 means every probe confirmed its assumption. A probe runs
alone as well, for example:

```bash
nvcc -std=c++17 -O2 -gencode arch=compute_100a,code=sm_100a gpu/probes/h1_tmem_a.cu -o h1_tmem_a && ./h1_tmem_a
```

## How they work

`probe.h` holds one kernel that interprets a plan: copy an operand image into 1024-byte-aligned shared memory
(`fence.proxy.async`), allocate tensor memory, write regions of it with `tcgen05.st.32x32b` (each thread its own
lane), issue a list of `tcgen05.mma.cta_group::1.kind::f16` from one thread (A from shared memory or tensor memory),
commit them to an mbarrier, wait, read regions back with `tcgen05.ld.32x32b`, and free. The host lays out the operands
in the canonical 128-byte-swizzled layouts (checked at start-up against a second statement of those layouts), builds
the plans, and checks the results exactly: all operands are small integers or multiples of 1/4, so every product and
sum is exact in f32 whatever the order of accumulation (except H5's, which measures the error).

The encodings reuse TinyGEMM's, which ran on a B200 (`gpu/Gpu.rac`: `smemDesc`, `instrDesc`, the `tcgen05` and
mbarrier templates): the shared-memory descriptor with SBO 1024, version 1 and 128-byte swizzle, and the instruction
descriptor 136316048 (bf16 × bf16 → f32, both K-major, M = N = 128). Every probe includes that path as a control or
as its measurement, so a broken probe shows as a failed control rather than as a false verdict.

Robustness:
- **Each case runs in its own forked process**, which alone touches CUDA, with a 60-second alarm. A fault that
  poisons the context (an illegal instruction, a trap) ends only that case. The child's output is line-buffered, so a
  killed case keeps what it printed, and the alarm's handler prints the stage the kernel reached before exiting.
  `run.sh` pins one GPU (`CUDA_VISIBLE_DEVICES`, default 0), since every case creates a context.
- **Every CUDA call is checked.** A failed case prints the error and the last stage the kernel reached (allocation,
  stores, MMAs issued, MMAs completed, loads, free), which thread 0 records in mapped host memory so that it survives
  the fault.
- **The mbarrier wait is bounded** (about two seconds of `clock64`); on expiry the kernel records the timeout and
  traps.

## Reading the output

Each case prints `== <probe> <case>`, its diagnostics, then one result line: `PASS`, `FAIL` (ran, wrong data),
`ERROR` (a CUDA error; the line before names it and the stage reached), `TIMEOUT` (the alarm fired) or `CRASH`. Each
probe ends with `-- <probe> verdict: …`.

**H1.** `control-*` (A and B in shared memory) must pass, or nothing else means anything. `decode` prints, for two
K = 16 MMAs reading A at columns 256 and 264, the column (relative to 256) and half each k came from, as lane 0 saw it,
and names the layout that map matches; it passes when that is A23's. The `<layout>-perm` and `<layout>-int` cases run
the whole 128 × 128 × 128 product with P written as each hypothesis says: `a23` (two per column, lower k in the low
half, 8 columns per step), `swapped` (lower k in the high half), `unpacked-lo` and `unpacked-hi` (one per column, 16
columns per step). In `-perm` cases a wrong element names the k it came from. Verdict and consequence:
- `A23 HOLDS`: `storeP` as `ATTENTION.md` §3.4 specifies it.
- `A23 FALSE; the layout is swapped`: `storeP` must swap its `cvt.rn.bf16x2.f32` operands.
- `A23 FALSE; the layout is unpacked-…`: P needs 128 columns; the tensor-memory map of §2.2 must change.
- `A23 FALSE and no variant matches`: P goes through shared memory (§2.3's fallback); decode's map shows what the
  hardware read.

**H2.** `control-*` stores B K-major (TinyGEMM's path). `a24-*` is the design's MN-major descriptor (transpose bit,
LBO 16384, SBO 1024); `swapped-*` exchanges LBO and SBO. A failing `-perm` case prints, for row 0 and ten columns
across both halves of N, the k it read against the k wanted: a wrong LBO shows in columns 64 and up, a wrong SBO or K
step in the key order everywhere.

**H3.** `ldst.x32@c` (one `.x32` store and one `.x32` load at column c, the rest by `.x8` at multiples of 8),
`ldst.x4@388` and `ldst.x4@444` (one `.x4` store and load at 4-column offsets inside P's columns, as `storeP` writes
P), `mmaD@c` (D at column c) and `mmaA@c` (A in tensor memory at column c, packed as A23 says). `mmaA@256` runs first
as the baseline of the A cases: when it fails, A23's packing (or A in tensor memory altogether) is in doubt, the other
A cases are reported INCONCLUSIVE, and H1 is where to look. A wrong placement prints the word found, which names the
lane, column and case it was written for (tensor memory keeps an earlier case's words, so every word carries its
case's number). The probe ends with the lists of cases that work and that fail; its exit status counts the offsets the
design uses (multiples of 64 and the `.x4` offsets) and the A baseline. A failure at 32, 96, 160 or 224 alone means
`splitTmem` (§3.1) must require multiples of 64.

**H5.** Per range (`uniform`: Q, K in [−1, 1]; `peaked`: Q in [−8, 8]), over four random 128 × 128 × 128 products: the
error of each element relative to Σ|q·k|, in units of 2⁻²⁴ (max, mean, and signed mean, which shows a truncating
accumulator as a bias toward zero), and the relative error over elements without heavy cancellation, for the tensor
cores and, for comparison, a sequential and a pairwise f32 sum on the host. `PASS` when every element is within
128 · 2⁻²⁴ · Σ|q·k|, the sequential-sum bound §1.3 assumes; otherwise T1's score term must use the measured constant.

## Checking without a GPU

`gpu/check.sh` compiles every probe against `gpu/stub/` with a host `clang++`, after rewriting the inline assembly of
`probe.h` into stub calls over its operands (`stub/asm_calls.py`). That checks the C++ and the asm operands, not the
PTX templates, which only ptxas can.
