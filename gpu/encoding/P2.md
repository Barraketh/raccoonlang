# Paged attention P2: decode with append

Status: built (2026-10-01), as §9 records: `Core.rac`'s paged-decode section, `examples/paged_append.rac`,
`examples/paged_decode.rac` and `examples/paged_combine.rac`, `harness/paged_decode_test.cu`, and the mutant tables
`rejected/paged_append_mutants.py`, `rejected/paged_decode_mutants.py` and `rejected/paged_combine_mutants.py`. P1 moved
to the cache layout of §1. Checked by generation, the certificate, the mutants and a compile against `gpu/stub/`, and
the harness against a host mock; not run on hardware. It is the step after P1 (`gpu/encoding/PAGED.md` §4). It builds
on A2's single-tile kernel (`gpu/encoding/Attention.rac`), not on A3's ping-pong: decode is bound by loading the cache,
and one query tile per CTA is enough to keep the loads going. FA4 facts are from Dao-AILab `flash-attention` at
`616b0e8` (`flash_attn/cute/flash_fwd_sm100.py`, `interface.py`).

## 1. The target

**Decode.** Each of `B` sequences has one new query token per head, and `len_b` keys in the cache before this step.
- `Hq = G · Hkv` query heads, with `G` query heads per KV head (grouped-query attention); head dimension 128.
- **The cache.** K and V are each `[pages, 128, Hkv, 128]` bf16, FA4's layout and vLLM's (`interface.py` 781–782):
  a page holds 128 consecutive positions, and each position holds every KV head. It is addressed as the rank-2 tensor
  `[pages · 128, Hkv · 128]`, so position `i` of page `p`, head `h`, is row `128p + i`, columns `128h` to `128h + 127`.
  P1's layout, `[pages, H, 128, 128]`, moves to this one, so that P1, P2 and FA4 read one cache.
- **Pages of 128 keys**, as P1 and as FA4's TMA path, which assumes the page size equals its key block
  (`flash_fwd_sm100.py` 3290).
- **The table** `block_table [B, maxPages]` u32, as P1, and **the lengths** `lens [B]` u32.
- **One query per sequence** (`q_len = 1`). Speculative decoding (`q_len > 1`) needs a rank-3 Q map (§6).

**Three kernels**, launched in order on one stream:
1. **Append** writes the new token's K and V into the cache at position `len_b`.
2. **Attention** reads the cache, `len_b + 1` keys per sequence, split over key blocks, and writes partial results.
3. **Combine** merges the partial results into O and LSE.

FA4 runs the same decode with its forward kernel (`pack_gqa`, `num_splits`), then its combine kernel. It does not
append; vLLM appends in a separate kernel, as here.

## 2. Append

**The work.** One warp per `(b, h)`. The new position is `pos = lens[b]`:
1. `j = pos / 128`; refuse if `j ≥ maxPages`;
2. `p = block_table[b][j]`; refuse if `p ≥ pages`;
3. claim page `p`'s rows of head `h` for sequence `b` (below); refuse if the claim fails;
4. write `k_new[b][h]` to K's row `128p + pos mod 128`, columns `128h …`, and `v_new[b][h]` likewise: each lane
   stores 8 bytes of K and 8 of V, so the 32 lanes cover the head's 256-byte row.

Lane 0 writes `appended[b · Hkv + h]`: 1 if the warp appended, 0 if it refused. A refusal is not a fault. The host
reads `appended`, and a sequence whose append was refused has a cache without its new token. (The design called it
`status`, a name the generated launcher declares itself.)

**Why a claim.** Where the writes land is decided by the table, which is run-time data. If two sequences' tables
name one page as their last, two warps write the same cache rows. That is a race on the cache, whatever the
attention kernel does afterwards. P1 needed no fact about the table, because it only reads. P2 writes, so it needs
one: no other sequence writes the rows this warp writes.

There are two ways to get that fact:
- **A launch contract:** the caller promises distinct last pages, as P1's contract promises valid pages. Safety
  then depends on the caller.
- **A checked claim:** the kernel establishes the fact itself, with one atomic per warp.

P2 uses the claim. Its cost is one 64-bit `atom.cas` per `(b, h)` and one word per `(page, head)`.

**The claim.** `owners [pages · Hkv]` u64 holds, for each `(page, head)`, `epoch · 2³² + b` of its last claim.
`epoch` is a kernel parameter that the host increases at every launch. Lane 0 of warp `(b, h)`, with
`mine = epoch · 2³² + b`:
1. reads `cur = owners[p · Hkv + h]`, single-copy atomic: a naturally aligned 64-bit `ld.relaxed.gpu`, so a torn read
   cannot pair this launch's epoch with another claim's sequence (OBLIGATIONS.md A41);
2. if `cur`'s epoch is this launch's: the claim holds iff `cur = mine`;
3. else: the claim holds iff `atom.cas(owners[w], cur, mine)` returns `cur`, that is, iff it stored `mine`.

Lane 0 alone reads `lens[b]` and the table. It then broadcasts the result and the claimed row with `shfl.sync`, so
every lane writes the row lane 0 claimed, by data flow, whatever the table holds.

**Freshness.** Owners start at 0 and epochs at 1, and the launcher refuses epoch 0, so that a launch finds no claim of
its own epoch before it starts. That is about which appends succeed, not about safety: the claim is exclusive for any
start values (below).

**Why the claim is exclusive.** In one launch, every write to an owner word stores this launch's epoch. So once a word
holds this launch's epoch, no claim changes it, and every later claim of it holds iff it is for the same sequence.
Two warps whose claims of one word both hold therefore have one sequence `b`. They have one head, so one `(b, h)`,
so they are one warp. The step-3 CAS needs no retry: if it fails, the word already holds this launch's epoch, with
another sequence, since the warps claiming one word are of one head and distinct sequences.
`harness/claim_model.py` checks this on every interleaving of three warps, which check.sh runs.

Nothing about the host's epochs can make two sequences' claims both hold. A reused epoch can make a claim fail, or
re-admit a word a sequence claimed in an earlier launch with that epoch, by step 2 with no CAS; it never admits two.

**The argument holds within one launch.** Two launches that share a cache and its owners must not run concurrently:
on two streams with epochs 5 and 6, each would see the other's epoch as old, and both CAS steps would succeed. The
launch contract says so: launches that share a cache and its owners run one at a time, as on one stream. Any kernel
that writes memory has this contract already: the attention kernel's reads of the cache would race with a concurrent
append too. The contract also says that nothing writes an input (`lens`, the table) during a launch: a concurrent
writer of an input is a race on the input.

**In Raccoon.** The claim's success is a fact about run-time data, and it holds only where the claim's code ran and
succeeded. It is an unrestricted sealed value minted inside the arm that runs on success, and confined to that arm's
scope. As designed (§9 has the signatures as built):

```raccoon
// The page owners of a cache: one u64 word per (page, KV head), and the launch's epoch.
sealed struct Owners (l: Lifetime) : Type { scope = l }
 | mk (name: String)(pages: Expr)(heads: Nat)(epoch: Expr) : Owners(l)

// Sequence `b`'s warp holds the rows of `page` for its head in this launch.
sealed struct Claimed (l: Lifetime) : Type { scope = l }
 | mk (page: Expr)(seq: Expr)(head: Expr) : Claimed(l)

// Claims `page` for this warp's (sequence, head), then runs `held` where the claim holds and `refused` elsewhere.
def withClaim {…}(e: Ctx(l, warp))(owners: Owners(L))(page: Val(S, u, DType.u32))
    (held: (m: Lifetime) -> Ctx(m, warp) -> Claimed(m) -> Ctx(m, warp))
    (refused: (m: Lifetime) -> Ctx(m, warp) -> Ctx(m, warp)): Ctx(l, warp)

// Writes the warp's new K and V rows into the claimed page. The row is computed from the claim and the sequence's
// length, never taken from the caller.
def appendRow {…}(e: Ctx(m, warp))(c: Claimed(m))(cache: PagedCache(L))(knew: NewKV(L))(lens: Lengths(L)): Ctx(m, warp)
```

`warp` stands for the group of the warp's lanes, and `{…}` elides implicit binders. The names are proposals.
- **No linearity** for `Claimed` itself. Exclusivity between warps comes from the atomic. Disjointness between lanes
  comes from the lane's column, computed in `appendRow`. (As built, the arm also gets a linear `AppendOwn`, so the
  row is written exactly once; §9.)
- **Scope does the work.** `Claimed(m)` belongs to the arm's scope `m`, so no code outside the arm can write the page.
  That is the pilot's proposal for open question 3 (`gpu/SEPARATION_PILOT.md` §6): a fact about run-time contents
  that lives only in the scope where it was established. (As built, the arm's fixed result type, the emitter alone,
  confines it as much as the scope does; §9.)

## 3. Attention

A2's kernel with five changes; the roles and protocols of `Attention.rac` are unchanged.
- **The query tile is packed.** CTA `(s, b · Hkv + h)` takes the `G` query heads of KV head `h`, rows `b · Hq + h · G`
  to `+ G − 1` of Q `[B · Hq, 128]`, by a Q box `G` rows high. The tile's other `128 − G` rows are never loaded. Their
  scores and probabilities are garbage, since rows of `S = QKᵀ` and of `PV` depend only on their own Q and P rows, and
  the epilogue stores only rows below `G`. They hold no protocol state.
- **The keys are paged and of a run-time length.** `n_b = ⌈(len_b + 1) / 128⌉` blocks, through P1's `fillPage` with
  the new layout: rows `128p`, columns `128h` and `128h + 64`. The mask keeps keys `kv < len_b + 1`. The roles count a
  split's blocks from 0, so to them a split is a sequence of its own keys, `len_b + 1 − 128 · first` of them: A2's
  non-causal `Mask` with that limit, and no new constructor (the design proposed one).
- **Split over key blocks.** `splits` is a launch parameter and `grid.x = splits`. Split `s` takes blocks
  `[s · c, min(n_b, (s + 1) · c))` with `c = ⌈n_b / splits⌉`, computed by dividing by `gridDim.x`, which is never 0. An
  empty range writes O = 0 and LSE = −∞. It still runs one block, with no keys: `loopPeeled` runs at least one
  iteration, so the prologue's count is at least 1 (`count ≥ 1`), and every role runs it. Its sum of probabilities is 0, so its LSE is −∞ and its Ô
  times `1/l` would be NaN; `storeO` stores its O as 0.
- **The trip count is computed once, by every thread.** The kernel's prologue, before the roles split, reads `lens[b]`
  at one address of a read-only input and computes `n_b` and the split's range, so every role runs the same trip count
  (M11). No new assumption is needed: a read-only input is not written during the launch, the same contract TMA loads
  of the cache already rely on (OBLIGATIONS.md M10). The roles take the count as A2's take theirs; a role that ran
  another count would deadlock, which no type refuses (§5).
- **Partial outputs.** O (f32) and LSE go to rows `((s · B + b) · Hkv + h) · G + g` of `Opart [splits · B · Hq, 128]`
  and `LSEpart`, LSE in natural-log units as A2's. The row is computed by the core from the CTA's indices (the
  `AttnOut`'s first row `s · B · Hq + (b · Hkv + h) · G`, and the thread's `g`), so CTAs write disjoint rows, as
  `storeO` does today.

**Why it is safe.** P1's argument (`PAGED.md` §3) plus disjoint partial rows: the kernel writes only its own rows of
`Opart` and `LSEpart`. The cache is read-only in this launch, since the append was the previous launch on the stream.

**What the table decides** is correctness, as in P1. A refused append leaves the sequence's last key unwritten, which
the host knows from `appended`.

## 4. Combine

A SIMT kernel: one warp per output row `(b, hq)`, each lane 4 columns.
- **Weights.** Read `LSEpart` for every split, take `M = max`, weight split `s` by `w_s = e^{LSE_s − M}`, computed as
  `2^{(LSE_s − M) · log₂ e}`. A2's LSE is in natural-log units (the design said log₂). An empty split's LSE is −∞, so
  its weight is 0, and its O is 0.
- **Output.** `O = Σ w_s · O_s / Σ w_s` (bf16, A2's conversion) and `LSE = M + ln Σ w_s`, computed as
  `M + log₂(Σ w_s) · ln 2`.
- **Lengths.** `len_b + 1 ≥ 1`, so at least one split is non-empty and `M` is finite. The prologue computes
  `n_b = len_b / 128 + 1` and a split's keys `(len_b − 128 · first) + 1`, which do not wrap. A length of
  2³² − 1 would make the first split's keys wrap to 0, a wrong result but no unsafe access; the launch contract
  requires `lens[b] < 2³² − 1`.

The rows are disjoint by index; every input is read-only.

## 5. Checks

- **Examples** (each generates, passes `render`'s certificate and compiles against the stubs):
  - `paged_append.rac`;
  - `paged_decode.rac`;
  - `paged_combine.rac`, or one example rendering the three.
- **A harness** against a host reference:
  - pages shuffled across sequences, lengths from 1 to several thousand, `G ∈ {1, 4, 8}`, `splits ∈ {1, 3, 8}`;
  - a table whose last pages collide: exactly one of the colliding sequences appends, every other is refused, and
    `appended` says which;
  - out-of-range table entries: refused, never written;
  - an epoch reused across two launches: claims refused, never doubled.
  It is validated against a host mock until hardware time is available.
- **Mutants:**
  - writing a cache row outside `withClaim`'s held arm;
  - `Claimed` returned out of the arm;
  - a caller-chosen row;
  - a write to `Opart` at another CTA's row;
  - an attention role that computes its own trip count from something other than `lens`. Not built: the roles take
    their count as a `Val`, as A2's do, so a loader that loops another number of times type-checks. Roles that
    disagree deadlock, and none can get a phase ahead (M11), so it is not a race. Refusing it would need the block
    index to be a sealed value that only a loop over the CTA's sealed range makes, and the fills and the mask to take
    it; that changes A2's roles, examples and checks, and is left for review.

## 6. Later

- **Speculative decoding** (`q_len > 1`): packed rows `(position, head)`, by a rank-3 Q map `[B · q_len, Hq, 128]` with
  box `(64, G, q_len)`, and a causal mask among the new positions. An append spanning two pages claims both.
- **Appending inside the attention kernel.** The writing CTA would read its own write, which needs a proxy fence. Other
  CTAs must not read the rows written, which a claim cannot show: a sequence sharing the page as a prefix reads it
  from another CTA, in the same launch. That needs readers to claim too (shared and exclusive claims), or a contract.
  It saves one launch per step. Measure first.
- **Combining inside the attention kernel**, by a last-CTA counter, also saves a launch.

## 7. Hardware

Decode is bound by the cache's bandwidth: a block of 128 keys is 64 KB of K and V, and its two MMAs on 128 padded
rows take less time on one SM than loading it does. `cta_group::2` does not apply: FA4 uses it only without split-KV
and with more than 256 packed query rows (`interface.py` 1080–1094), so its decode runs at `cta_group::1`. So "competitive" here means FA4's decode time at matching `splits`, near the B200's memory
bandwidth. That bar may come before A3's: the hardware decision is the user's (§8, 5).

## 8. Decisions

1. **Three kernels**, append, attention, combine, rather than one fused kernel.
2. **FA4's cache layout** `[pages, 128, Hkv, 128]` for P1 and P2 alike.
3. **Appends are checked by a claim**, an atomic per `(page, head)` with launch epochs, rather than a launch contract
   on distinct last pages. A failed claim refuses the append and reports it in `appended`.
4. **The claim is a fact of the success arm.** The atomic gives exclusivity between warps. The arm's scope, and its
   fixed result type (the emitter alone), confine `Claimed(m)` to the arm. Linearity gives exactly once: the arm
   receives a linear `AppendOwn(m)` that `appendRow` uses up, so it writes the row once, neither twice nor in a loop,
   and not zero times.
5. **Hardware for P2** once the three kernels pass the harness on the mock, if the user agrees that decode, which is
   memory-bound, meets the bar without `cta_group::2`.
6. **`q_len = 1` first**; speculative decoding with the rank-3 Q map after.

## 9. P2 as built

As §1–§5 design it, with these decisions where the design left room (OBLIGATIONS.md A40–A42, M17, §6.11):

- **P1's layout.** `fillPage` loads rows `128p` at columns `128h` and `128h + 64`. P1's launcher gains `cols_kv`, which
  must be `Hkv · 128`, and refuses `pages · 128 ≥ 2³¹` where it refused `pages · Hkv · 128 ≥ 2³¹`.
- **The append's signatures.**
  ```raccoon
  def withClaim {…}(e: Ctx(l, warpCta))(lens: Lengths(L))(table: PageTable(L))(claims: Claims(L))(own: ClaimOwn(L))
      (held: (m: Lifetime) -> Ctx(m, warpCta) -> Claimed(m) -> AppendOwn(m) -> Ctx(m, warpCta)): Ctx(l, warpCta)
  def appendRow {…}(e: Ctx(n, warpCta))(c: Claimed(m))(once: AppendOwn(m))(cache: PagedCache(L))(knew: NewKV(L))
      : Ctx(n, warpCta)
  ```
  - The page is the core's: lane 0 of `withClaim` reads `lens[b]` and the table itself, and refuses an entry outside
    the table or the cache. The caller gives no page, row or sequence. Lane 0 broadcasts the claimed row with the
    result, so the lanes do not read the table again.
  - `Claims` holds the owners, the epoch, `appended` and the page count. `ClaimOwn` is linear, so a warp claims, and
    reports, once.
  - There is no `refused` arm: the core writes `appended`, and nothing else happens on a refusal.
  - `held` is unrestricted, so it captures no linear value, and returns the emitter alone. `Claimed` is unrestricted;
    `AppendOwn` is linear, so the arm writes the row exactly once (decision 4). No mutant is refused by the scope alone:
    the arm's result type already refuses every channel out of it (`claim_leaves_arm`).
- **One warp per CTA.** The append and combine kernels launch CTAs of one warp (`warpCta`), so the broadcast flag is
  uniform and the held arm keeps the warp's group.
- **The claim's code.** `ld.relaxed.gpu.global.b64` and `atom.relaxed.gpu.global.cas.b64` through `cvta.to.global`
  (A41), and `shfl.sync.idx` for the two broadcasts (A42), each a `Stmt.asm`. Step 2 sets the flag to `cur = mine`,
  step 3 to `atom.cas(…) = cur`. The atomic path where the CAS fails has not run (the mock performs each claim at
  once); `harness/claim_model.py` checks it on every interleaving instead.
- **The new row.** Each lane copies 8 bf16 elements of K and 8 of V, element by element (`Cuda.Expr` has no vector
  type). The cache index is 64-bit.
- **The decode's Q.** `fillGroup` loads two boxes of `G` rows into the stage's 128-row halves, expecting their
  `256 · G` bytes; that a short box lands as the first rows of a full one is A40.
- **The decode's output.** A3a's row-carrying `AttnOut` (the thread's row) gains the CTA's first row and the
  condition where O is kept, for the empty split; `storeO` serves every kernel. The row is the builder's
  (`rowInTile`, `32 · (warp mod 4) + lane`, below G) and the first row too, and the decode CTA's `OOwn` is the softmax
  warpgroup's (warps 4–7), as A2's (M12).
- **The launchers.** Each takes its kernel's parameters, the arrays for the maps in their place, then the extents
  only it reads: the decode's `splits`, `pages`, `rows_q`, `rows_kv`, `cols_kv` and `dim`, the append's `B`. The decode
  launcher refuses `splits = 0` and `splits · B · Hq · 128 ≥ 2³¹`; the kernel divides by `gridDim.x`. The append
  launcher refuses `epoch = 0`. The combine launcher takes `rows` (`B · Hq`), so one combine kernel serves every `G`.
- **`gpu/Cuda.rac`.** A launched kernel without tensor maps printed no `#include`, so the append and combine kernels'
  `__nv_bfloat16` and launchers did not compile. `Cuda.headers` now states one rule per header: `cuda.h` for tensor
  maps, `cuda_bf16.h` for tensor maps or bf16 parameters, `cuda_runtime.h` for a launcher. Every existing kernel prints
  as before (checked on every example of `gpu/examples` and `gpu/encoding/examples`).
- **The examples.** Hkv = 8; the decode example renders G = 1, 4 and 8 (`paged_decode_g1`, `_g4`, `_g8`).
