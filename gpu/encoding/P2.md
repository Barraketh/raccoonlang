# Paged attention P2: decode with append

Status: design, not implemented (2026-10-01). It is the step after P1 (`gpu/encoding/PAGED.md` §4). It builds on A2's
single-tile kernel (`gpu/encoding/Attention.rac`), not on A3's ping-pong: decode is bound by loading the cache, and one
query tile per CTA is enough to keep the loads going. FA4 facts are from Dao-AILab `flash-attention` at `616b0e8`
(`flash_attn/cute/flash_fwd_sm100.py`, `interface.py`).

## 1. The target

**Decode.** Each of `B` sequences has one new query token per head, and `len_b` keys in the cache before this step.
- `Hq = G · Hkv` query heads, with `G` query heads per KV head (grouped-query attention); head dimension 128.
- **The cache.** K and V are each `[pages, 128, Hkv, 128]` bf16, FA4's layout and vLLM's (`interface.py` 781–782):
  a page holds 128 consecutive positions, and each position holds every KV head. It is addressed as the rank-2 tensor
  `[pages · 128, Hkv · 128]`, so position `i` of page `p`, head `h`, is row `128p + i`, columns `128h` to `128h + 127`.
  P1's layout, `[pages, H, 128, 128]`, moves to this one, so that P1, P2 and FA4 read one cache.
- **Pages of 128 keys**, as P1 and as FA4's TMA path, which assumes the page size equals its key block
  (`flash_fwd_sm100.py` 3290).
- **The table** `block_table [B, maxPages]` u32, as P1, and **the lengths** `lens [B]` u32.
- **One query per sequence** (`q_len = 1`). Speculative decoding (`q_len > 1`) needs a rank-3 Q map (§6).

**Three kernels**, launched in order on one stream:
1. **Append** writes the new token's K and V into the cache at position `len_b`.
2. **Attention** reads the cache, `len_b + 1` keys per sequence, split over key blocks, and writes partial results.
3. **Combine** merges the partial results into O and LSE.

FA4 runs the same decode with its forward kernel (`pack_gqa`, `num_splits`), then its combine kernel. It does not
append; vLLM appends in a separate kernel, as here.

## 2. Append

**The work.** One warp per `(b, h)`. The new position is `pos = lens[b]`:
1. `j = pos / 128`; refuse if `j ≥ maxPages`;
2. `p = block_table[b][j]`; refuse if `p ≥ pages`;
3. claim page `p`'s rows of head `h` for sequence `b` (below); refuse if the claim fails;
4. write `k_new[b][h]` to K's row `128p + pos mod 128`, columns `128h …`, and `v_new[b][h]` likewise: each lane
   stores 16 bytes of K and 16 of V.

Lane 0 writes `status[b · Hkv + h]`: 1 if the warp appended, 0 if it refused. A refusal is not a fault. The host reads
`status`, and a sequence whose append was refused has a cache without its new token.

**Why a claim.** Where the writes land is decided by the table, which is run-time data. If two sequences' tables
name one page as their last, two warps write the same cache rows. That is a race on the cache, whatever the
attention kernel does afterwards. P1 needed no fact about the table, because it only reads. P2 writes, so it needs
one: no other sequence writes the rows this warp writes.

There are two ways to get that fact:
- **A launch contract:** the caller promises distinct last pages, as P1's contract promises valid pages. Safety
  then depends on the caller.
- **A checked claim:** the kernel establishes the fact itself, with one atomic per warp.

P2 uses the claim. Its cost is one 64-bit `atom.cas` per `(b, h)` and one word per `(page, head)`.

**The claim.** `owners [pages · Hkv]` u64 holds, for each `(page, head)`, `epoch · 2³² + b` of its last claim.
`epoch` is a kernel parameter that the host increases at every launch; owners start at 0 and epochs at 1. Lane 0 of
warp `(b, h)`:
1. reads `cur = owners[p · Hkv + h]`;
2. if `cur`'s epoch is this launch's: the claim holds iff `cur`'s sequence is `b`;
3. else `prev = atom.cas(owners[w], cur, epoch · 2³² + b)`: the claim holds iff `prev = cur`, or `prev` is this
   launch's epoch with sequence `b`.

Lane 0 then broadcasts the result with `__shfl_sync`.

**Why the claim is exclusive.** In one launch, every write to an owner word stores this launch's epoch. So once a word
holds this launch's epoch, no claim changes it, and every later claim of it holds iff it is for the same sequence.
Two warps whose claims of one word both hold therefore have one sequence `b`. They have one head, so one `(b, h)`,
so they are one warp. The step-3 CAS needs no retry: if it fails, the word already holds this launch's epoch.

Nothing about the host's epochs can make two sequences' claims both hold. A reused epoch can only make a claim fail.

**In Raccoon.** The claim's success is a fact about run-time data, and it holds only where the claim's code ran and
succeeded. It is an unrestricted sealed value minted inside the arm that runs on success, and confined to that arm's
scope:

```raccoon
// The page owners of a cache: one u64 word per (page, KV head), and the launch's epoch.
sealed struct Owners (l: Lifetime) : Type { scope = l }
 | mk (name: String)(pages: Expr)(heads: Nat)(epoch: Expr) : Owners(l)

// Sequence `b`'s warp holds the rows of `page` for its head in this launch.
sealed struct Claimed (l: Lifetime) : Type { scope = l }
 | mk (page: Expr)(seq: Expr)(head: Expr) : Claimed(l)

// Claims `page` for this warp's (sequence, head), then runs `held` where the claim holds and `refused` elsewhere.
def withClaim {…}(e: Ctx(l, warp))(owners: Owners(L))(page: Val(S, u, DType.u32))
    (held: (m: Lifetime) -> Ctx(m, warp) -> Claimed(m) -> Ctx(m, warp))
    (refused: (m: Lifetime) -> Ctx(m, warp) -> Ctx(m, warp)): Ctx(l, warp)

// Writes the warp's new K and V rows into the claimed page. The row is computed from the claim and the sequence's
// length, never taken from the caller.
def appendRow {…}(e: Ctx(m, warp))(c: Claimed(m))(cache: PagedCache(L))(knew: NewKV(L))(lens: Lengths(L)): Ctx(m, warp)
```

`warp` stands for the group of the warp's lanes, and `{…}` elides implicit binders. The names are proposals.
- **No linearity.** `Claimed` needs none. One warp's two writes of a row happen in program order. Exclusivity between
  warps comes from the atomic. Disjointness between lanes comes from the lane's column, computed in `appendRow`.
- **Scope does the work.** `Claimed(m)` belongs to the arm's scope `m`, so no code outside the arm can write the page.
  That is the pilot's proposal for open question 3 (`docs/SEPARATION_PILOT.md` §6): a fact about run-time contents
  that lives only in the scope where it was established.

## 3. Attention

A2's kernel with five changes; the roles and protocols of `Attention.rac` are unchanged.
- **The query tile is packed.** CTA `(s, b · Hkv + h)` takes the `G` query heads of KV head `h`, rows `b · Hq + h · G`
  to `+ G − 1` of Q `[B · Hq, 128]`, by a Q box `G` rows high. The tile's other `128 − G` rows are never loaded. Their
  scores and probabilities are garbage, since rows of `S = QKᵀ` and of `PV` depend only on their own Q and P rows, and
  the epilogue stores only rows below `G`. They hold no protocol state.
- **The keys are paged and of a run-time length.** `n_b = ⌈(len_b + 1) / 128⌉` blocks, through P1's `fillPage` with
  the new layout: rows `128p`, columns `128h` and `128h + 64`. The mask keeps keys `kv < len_b + 1`: a new sealed
  `Mask` constructor, whose limit is the sequence's length.
- **Split over key blocks.** `splits` is a launch parameter and `grid.x = splits`. Split `s` takes blocks
  `[s · c, min(n_b, (s + 1) · c))` with `c = ⌈n_b / splits⌉`. An empty range writes O = 0 and LSE = −∞.
- **The trip count is computed by every role.** Each role reads `lens[b]` at the same address of a read-only input and
  computes `n_b` and its range in the prologue, so every role runs the same trip count (M11). No new assumption is
  needed: a read-only input is not written during the launch, the same contract TMA loads of the cache already rely
  on.
- **Partial outputs.** O (f32) and LSE go to rows `((s · B + b) · Hkv + h) · G + g` of `Opart [splits · B · Hq, 128]`
  and `LSEpart`. The row is computed by the core from the CTA's indices, so CTAs write disjoint rows, as `storeO`
  does today.

**Why it is safe.** P1's argument (`PAGED.md` §3) plus disjoint partial rows: the kernel writes only its own rows of
`Opart` and `LSEpart`. The cache is read-only in this launch, since the append was the previous launch on the stream.

**What the table decides** is correctness, as in P1. A refused append leaves the sequence's last key unwritten, which
the host knows from `status`.

## 4. Combine

A SIMT kernel: one warp per output row `(b, hq)`, each lane 4 columns.
- **Weights.** Read `LSEpart` for every split, take `M = max`, weight split `s` by `w_s = 2^{LSE_s − M}` (LSE in log₂
  units, as A2's).
- **Output.** `O = Σ w_s · O_s / Σ w_s` (bf16, A2's conversion) and `LSE = M + log₂ Σ w_s`.
- **Lengths.** `len_b + 1 ≥ 1`, so at least one split is non-empty and `M` is finite.

The rows are disjoint by index; every input is read-only.

## 5. Checks

- **Examples** (each generates, passes `render`'s certificate and compiles against the stubs):
  - `paged_append.rac`;
  - `paged_decode.rac`;
  - `paged_combine.rac`, or one example rendering the three.
- **A harness** against a host reference:
  - pages shuffled across sequences, lengths from 1 to several thousand, `G ∈ {1, 4, 8}`, `splits ∈ {1, 3, 8}`;
  - a table whose last pages collide: exactly one of the colliding sequences appends, every other is refused, and
    `status` says which;
  - out-of-range table entries: refused, never written;
  - an epoch reused across two launches: claims refused, never doubled.
  It is validated against a host mock until hardware time is available.
- **Mutants:**
  - writing a cache row outside `withClaim`'s held arm;
  - `Claimed` returned out of the arm;
  - a caller-chosen row;
  - a write to `Opart` at another CTA's row;
  - an attention role that computes its own trip count from something other than `lens`.

## 6. Later

- **Speculative decoding** (`q_len > 1`): packed rows `(position, head)`, by a rank-3 Q map `[B · q_len, Hq, 128]` with
  box `(64, G, q_len)`, and a causal mask among the new positions. An append spanning two pages claims both.
- **Appending inside the attention kernel.** The writing CTA would read its own write, which needs a proxy fence. Other
  CTAs must not read the rows written, which a claim cannot show: a sequence sharing the page as a prefix reads it
  from another CTA, in the same launch. That needs readers to claim too (shared and exclusive claims), or a contract.
  It saves one launch per step. Measure first.
- **Combining inside the attention kernel**, by a last-CTA counter, also saves a launch.

## 7. Hardware

Decode is bound by the cache's bandwidth: a block of 128 keys is 64 KB of K and V, and its two MMAs on 128 padded
rows take less time on one SM than loading it does. `cta_group::2` does not apply: FA4 uses it only without split-KV
and with more than 256 packed query rows (`interface.py` 1080–1094), so its decode runs at `cta_group::1`. So "competitive" here means FA4's decode time at matching `splits`, near the B200's memory
bandwidth. That bar may come before A3's: the hardware decision is the user's (§8, 5).

## 8. Decisions

1. **Three kernels**, append, attention, combine, rather than one fused kernel.
2. **FA4's cache layout** `[pages, 128, Hkv, 128]` for P1 and P2 alike.
3. **Appends are checked by a claim**, an atomic per `(page, head)` with launch epochs, rather than a launch contract
   on distinct last pages. A failed claim refuses the append and reports it in `status`.
4. **The claim is a scoped fact**, `Claimed(m)` in the success arm's scope, unrestricted, rather than a linear token.
5. **Hardware for P2** once the three kernels pass the harness on the mock, if the user agrees that decode, which is
   memory-bound, meets the bar without `cta_group::2`.
6. **`q_len = 1` first**; speculative decoding with the rank-3 Q map after.
